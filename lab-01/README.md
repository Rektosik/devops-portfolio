- Вміст `.editorconfig` та пояснення
- **Чим відрізняються global / local / system?**
`--system` діє для всіх користувачів комп'ютера, `--global` для мого користувача (`~/.gitconfig`), `--local` лише для одного репозиторію (`.git/config`). Пріоритет: local → global → system. Тому в окремому репозиторії можна вказати інший email, не чіпаючи глобальні налаштування.

**Навіщо `user.email`?**
Він записується в кожен коміт як автор. GitHub за email привʼязує коміти до профілю, тому email має збігатися з підтвердженим email акаунта. Інакше коміти не будуть привʼязані до мого профілю.

**`autocrlf` vs `.editorconfig`:**
У Windows кінець рядка CRLF, у Linux і macOS LF. `core.autocrlf = true` працює на рівні Git: при checkout перетворює LF на CRLF, а при коміті повертає LF. `.editorconfig` працює на рівні редактора: задає, які кінці рядків і відступи редактор пише у файл. Разом вони не дають змішаних кінців рядків і зайвих диффів.

- **Чим Compose v2 відрізняється від v1?**
v2 це плагін Docker CLI, який викликається як `docker compose` (через пробіл) і входить до складу Docker Desktop. v1 це окремий застарілий Python-застосунок `docker-compose`, який більше не підтримується й не отримує оновлень.


## Завдання 3. GitHub і доступ

- **Чому приватний ключ не можна передавати?**
Приватний ключ це доказ моєї особи для GitHub. Хто ним володіє, може пушити код від мого імені, змінювати мої репозиторії й видавати себе за мене. Публічний ключ можна розповсюджувати вільно: він дозволяє лише перевірити підпис, але не створити його. Тому приватний ключ залишається на моїй машині, захищений passphrase, не потрапляє в репозиторій (патерни `id_*` у `.gitignore`) і не пересилається в месенджерах. Якщо ключ скомпрометовано, треба видалити публічний ключ з GitHub і згенерувати нову пару.


## Завдання 4. Портфоліо-репозиторій
- https://github.com/Rektosik/devops-portfolio/tree/main
- Одна тека на кожну лабораторну дає передбачувану навігацію, а `final/` призначено для фінального проєкту. Порожні теки збережено через файли `.gitkeep`, бо Git не відстежує порожні теки.

**`.gitignore`:** виключає службові файли ОС і редакторів (`.DS_Store`, `Thumbs.db`, `.vscode/`), секрети (`.env`, `*.pem`, `id_*`), залежності та артефакти збірки (`node_modules/`, `__pycache__/`, `dist/`). Це потрібно робити з самого початку, бо секрет, який потрапив у коміт, залишається в історії, навіть якщо файл потім видалити.

**Ліцензія: MIT.** Дуже проста й вільна ліцензія: дозволяє використовувати, змінювати й розповсюджувати код за єдиної умови зберегти копірайт. Для навчального портфоліо це найпростіший варіант без додаткових зобовʼязань.

## Рішення та альтернативи
| Рішення | Чому так | Альтернатива | Коли було б неправильно |
|---|---|---|---|
| Гілка `main` за замовчуванням | Стандарт GitHub, збігається з ruleset | `master` | Якщо наявна інфраструктура команди вже на іншій назві |
| `autocrlf = true` | Працюю на Windows | `input` (Linux/macOS), `.gitattributes` з `eol=lf` | Якщо скрипти bash чи Dockerfile ламаються на CRLF у робочій теці |
| `.editorconfig` з LF | DevOps-файли (shell, Dockerfile, YAML) чутливі до CRLF | Налаштування окремо в кожному редакторі | Якщо цільова платформа вимагає CRLF (батники Windows) |
| nvm-windows | Нативний менеджер версій для Windows | `fnm`, `volta`, `mise` | У команді, де всі на Linux/macOS, краще кросплатформний інструмент зі спільним конфігом |
| Docker Desktop + Compose v2 | Найпростіше встановлення на Windows | Podman Desktop, Rancher Desktop | У великій компанії через умови комерційної ліцензії Docker Desktop |
| SSH-ключ Ed25519 | Коротший, швидший, сучасніша криптографія | RSA 4096 | Якщо сервер не підтримує Ed25519 |
| SSH замість HTTPS + токен | Не потрібно вводити токен, ключ відкликається окремо | HTTPS + Personal Access Token | За файрволом, що блокує порт 22 |
| Passphrase на ключі | Захист, якщо файл ключа витече | Ключ без passphrase (для CI) | Без passphrase на особистому ноутбуку, який можуть вкрасти |
| 2FA через застосунок | SMS вразливі до перехоплення SIM | Апаратний ключ / passkey (ще надійніше) | Покладатися лише на SMS для важливого акаунта |
| Публічний репозиторій | Вимога безкоштовного плану для правил гілок | Приватний репозиторій на платному плані | Якщо в коді є секрети чи комерційна таємниця |
| Один репозиторій на всі роботи | Єдине портфоліо, один набір правил і історія | Окремий репозиторій на кожну роботу | Якщо роботи мають різних власників чи рівні доступу |
| Ліцензія MIT | Проста й вільна | Apache-2.0 (патентний захист), GPL (відкриті похідні) | Якщо потрібно змусити відкривати похідний код або важливий патентний захист |
| Ruleset, а не classic branch protection | Гнучкіший, експортується в JSON, є режим Evaluate | Classic branch protection | Якщо потрібна функція, якої ще немає в рулсетах |
| 0 approvals у PR | Працюю сам, власний PR схвалити неможливо | ≥1 approval від іншої людини | У командному репозиторії |
| Порожній Bypass list | Правила діють і на власника, обійти процес неможливо | Bypass для довіреної ролі | Якщо потрібен аварійний доступ, наприклад зламаний CI блокує виправлення |
| Block force push і Restrict deletions | Історія `main` це джерело правди, її не можна втратити | Не блокувати | На особистих чорнових гілках, тому правило лише для `main` |
| Обовʼязковий PR навіть для однієї людини | Шаблон, чекліст, історія рішень, можливість відкоту | Прямі коміти | Якщо репозиторій одноразовий і ніхто його не читатиме |
| GitHub Projects для дошки | Автоматизації вбудовані (закрито issue / змерджено PR → Done) | Trello, Jira | Якщо команда вже працює в іншому трекері |
| Правила як код (JSON) | Версіонуються, відтворюються, перевіряються в PR | Налаштування вручну через UI | Для разового експерименту, де накладні витрати не виправдані |
