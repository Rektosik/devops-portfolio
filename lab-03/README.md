# Лабораторна робота 3: Власний DevOps-інструментарій

Три інструменти автоматизації, написані як «справжні» утиліти: з довідкою (`--help`), осмисленими кодами виходу, перевіркою параметрів без трасування стека, журналом запусків і документацією.

```
lab-03/
├── README.md
├── backup.sh              # резервне копіювання з перевіркою та ротацією
├── api_monitor.py         # монітор доступності HTTP/API-ендпоінтів
├── config/
│   ├── monitor.json       # основна конфігурація монітора
│   └── monitor.local.json # локальна конфігурація для перевірки без інтернету
└── hooks/
    └── pre-commit         # Git-хук: блокує коміти з потенційними секретами
```

**Середовище.** `backup.sh` запускається в Bash (на Windows це Git Bash, який встановлюється разом із Git; потрібні `tar`, `sha256sum`, `date`, `du`). `api_monitor.py` потребує Python 3 і не використовує сторонніх бібліотек. Якщо скрипт не запускається як `./backup.sh`, виконайте `bash backup.sh`.

## Спільні принципи

* **Довідка:** кожен інструмент має `--help` із призначенням, параметрами, кодами виходу та прикладом.
* **Коди виходу:** `0` означає успіх, різні причини помилок мають різні ненульові коди.
* **Перевірка параметрів:** відсутній параметр, неіснуючий файл чи некоректне значення дають зрозуміле повідомлення, а не трасування стека.
* **Журнал:** кожен запуск лишає записи у форматі `час [РІВЕНЬ] подія`.

## `set -euo pipefail`

Кожен bash-скрипт починається з `set -euo pipefail`. Це три окремі прапорці:

* **`-e` (errexit).** Скрипт зупиняється на першій команді, що завершилася з помилкою. Без нього скрипт іде далі після збою. У `backup.sh` це означало б, що після невдалого `tar` скрипт все одно перейшов би до ротації й видалив старі копії, хоча нового архіву немає: резервних копій не залишилось би взагалі.
* **`-u` (nounset).** Звернення до змінної, якій не присвоєно значення, вважається помилкою. Без нього друкарська помилка в імені змінної мовчки підставляє порожній рядок: команда `rm -rf "$DEST/"` із порожньою `$DEST` перетворюється на `rm -rf "/"`.
* **`-o pipefail`.** Код виходу конвеєра `cmd1 | cmd2` визначається не лише останньою командою: якщо будь-яка команда в ланцюжку завершилася з помилкою, помилкою вважається весь конвеєр. Без нього збій першої команди губиться, якщо остання відпрацювала успішно. Наприклад, у `du -h "$ARCHIVE" | cut -f1` помилка `du` лишилася б непоміченою, бо `cut` завершується успішно.

Також у `backup.sh` увімкнено `set -E`: без нього обробник помилок `trap ... ERR` не діяв би всередині функцій.

Прапорець `-e` не спрацьовує для команд у складі умов (`if`, `&&`, `||`), тому скрипт перевіряє результат критичних команд явно.

## 1. Скрипт резервного копіювання `backup.sh`

Архівує теку в `backup_<імʼя>_<РРРРММДД>_<ГГХХСС>.tar.gz`, перевіряє архів, записує контрольну суму `.sha256` і залишає лише задану кількість найновіших копій. Журнал пишеться в `<призначення>/backup.log`.

**Запуск:**
```bash
./backup.sh --source ./data --dest ./backups --keep 3 --exclude '*.log'
./backup.sh --help
```

**Параметри:**

| Параметр | Опис |
|---|---|
| `-s`, `--source ТЕКА` | що копіювати; обовʼязковий, тека має існувати |
| `-d`, `--dest ТЕКА` | куди класти архіви; обовʼязковий, створюється за потреби |
| `-k`, `--keep N` | скільки копій зберігати, ціле число не менше 1 (типово 5) |
| `-e`, `--exclude ШАБЛОН` | не включати файли за шаблоном; можна вказувати кілька разів |
| `-l`, `--log ФАЙЛ` | інший файл журналу (типово `<призначення>/backup.log`) |
| `-n`, `--dry-run` | лише показати, що було б зроблено, нічого не змінюючи |
| `-h`, `--help` | довідка |

**Коди виходу:**

| Код | Значення |
|---|---|
| `0` | успіх |
| `2` | неправильні або відсутні параметри |
| `3` | джерело не існує або не читається |
| `4` | не вдалося створити чи записати теку призначення або журнал (зокрема призначення всередині джерела) |
| `5` | `tar` не зміг створити архів (або архів із такою назвою вже існує) |
| `6` | архів створено, але перевірка цілісності не пройшла |

**Як працює:**
1. Перевіряє параметри (обовʼязкові, `--keep` є додатним цілим, джерело існує й читається, призначення не лежить усередині джерела).
2. Створює архів із суфіксом `.partial`.
3. Перевіряє, що архів читається повністю (`tar -tzf`).
4. Перейменовує `.partial` у готовий архів і записує `.sha256`, одразу підтверджуючи його.
5. Видаляє найстаріші архіви **цього ж джерела** понад ліміт `--keep` (разом з їхніми `.sha256`).

**Приклад: успішний запуск** (шляхи у вашому виводі будуть іншими):
```
$ ./backup.sh -s ./data -d ./backups -k 3 -e '*.log'
2026-11-17 22:37:18 [INFO] Старт: джерело=/c/Users/<ви>/demo/data призначення=/c/Users/<ви>/demo/backups зберігати=3 dry-run=0
2026-11-17 22:37:18 [INFO] Архів створено й перевірено: /c/Users/<ви>/demo/backups/backup_data_20261117_223718.tar.gz (4.0K)
2026-11-17 22:37:18 [INFO] Ротація не потрібна: архівів 1 із дозволених 3
2026-11-17 22:37:18 [INFO] Завершено успішно
```

**Приклад: ротація** (четвертий запуск при `--keep 3`):
```
2026-11-17 22:37:21 [INFO] Архів створено й перевірено: .../backups/backup_data_20261117_223721.tar.gz (4.0K)
2026-11-17 22:37:21 [INFO] Видалено старий архів: .../backups/backup_data_20261117_223718.tar.gz
2026-11-17 22:37:21 [INFO] Завершено успішно
```

**Приклад: dry-run:**
```
$ ./backup.sh -s ./data -d ./backups -k 3 -n -e '*.log'
2026-11-17 22:37:18 [INFO] Старт: джерело=... призначення=./backups зберігати=3 dry-run=1
2026-11-17 22:37:18 [INFO] [dry-run] було б створено архів: ./backups/backup_data_20261117_223718.tar.gz
2026-11-17 22:37:18 [INFO] [dry-run] було б виключено за шаблоном: *.log
2026-11-17 22:37:18 [INFO] Завершено (dry-run), нічого не змінено
```

**Приклади помилок:**
```
$ ./backup.sh -s ./nope -d ./backups
2026-11-17 22:37:21 [ERROR] Джерело не існує або це не тека: ./nope          (код 3)

$ ./backup.sh
Помилка: не вказано джерело (-s). Див. backup.sh --help                      (код 2)

$ ./backup.sh -s ./data -d ./backups -k abc
Помилка: --keep має бути цілим числом >= 1, отримано 'abc'                   (код 2)
```

**Перевірка цілісності пізніше:**
```bash
cd backups && sha256sum -c backup_data_20261117_223721.tar.gz.sha256
```

**Прийняті рішення:**
* **Тимчасовий файл `.partial` і лише потім перейменування.** Недописаний архів ніколи не виглядає як готова копія, а `trap` видаляє його, якщо скрипт перервано.
* **Перевірка `tar -t` і `.sha256`.** Перша підтверджує, що архів читається, друга дозволяє пізніше виявити пошкодження файлу. Контрольна сума лежить поруч з архівом, тож вона захищає від пошкоджень, але не від навмисної підміни.
* **Мітка часу в імені.** Імена сортуються за часом, тому ротація просто видаляє перші за списком. Ротація чіпає лише файли за шаблоном `backup_<імʼя>_<дата>_<час>.tar.gz` того самого джерела, тому копії інших джерел не страждають.
* **`--dry-run`.** Дозволяє безпечно перевірити параметри й побачити, що саме буде видалено.
* **Формат tar.gz замість zip.** Стандарт для Linux, зберігає права доступу й є в кожному дистрибутиві.

**Обмеження:** мітка часу з точністю до секунди (повторний запуск у ту саму секунду відхиляється із зрозумілим повідомленням); копіювання повне, не інкрементальне; архіви не шифруються; помилки параметрів, виявлені до готовності журналу, потрапляють лише у `stderr`.

## 2. Монітор доступності API `api_monitor.py`

Читає JSON-конфігурацію зі списком ендпоінтів, виконує до кожного GET-запит і порівнює отриманий HTTP-статус з очікуваним. Кожну перевірку записує в журнал `api_monitor.log` (поруч зі скриптом). Використовує лише стандартну бібліотеку Python.

**Запуск:**
```bash
python3 api_monitor.py --config config/monitor.json --timeout 5
python3 api_monitor.py --help
```
(У Windows використовуйте `python` замість `python3`.)

**Параметри:**

| Параметр | Опис |
|---|---|
| `--config ФАЙЛ` | JSON-файл конфігурації; обовʼязковий |
| `--timeout СЕК` | таймаут одного запиту, число більше нуля (типово 5) |
| `-h`, `--help` | довідка |

**Формат конфігурації** (`config/monitor.json`):
```json
{
  "endpoints": [
    { "name": "GitHub API", "url": "https://api.github.com", "expected_status": 200 },
    { "name": "HTTPBin Unauthorized Check", "url": "https://httpbin.org/status/401", "expected_status": 401 }
  ]
}
```
Поле `endpoints` має бути непорожнім списком; у кожного елемента `url` починається з `http://` або `https://`; `name` необовʼязкове; `expected_status` (типово 200) це число 100-599. Коди 4xx і 5xx не вважаються помилкою самі по собі: перевіряється збіг з очікуваним, тому ендпоінт, що має повертати `401`, вважається справним.

**Коди виходу:**

| Код | Значення |
|---|---|
| `0` | усі ендпоінти відповіли як очікувалось |
| `1` | є недоступні ендпоінти (мережа, таймаут) або неочікуваний статус |
| `2` | файл конфігурації не існує або не читається |
| `3` | некоректний JSON або неправильна структура конфігурації |
| `4` | неправильні параметри командного рядка |
| `5` | внутрішня помилка |

**Приклад виводу** (затримки у вас будуть іншими):
```
$ python3 api_monitor.py --config config/monitor.json
[OK] GitHub API (https://api.github.com) — 200 (312 ms)
[OK] HTTPBin Status 200 (https://httpbin.org/status/200) — 200 (540 ms)
[OK] HTTPBin Unauthorized Check (https://httpbin.org/status/401) — 401 (498 ms)
```

**Приклади помилок:**
```
[FAIL] Local 404 (http://127.0.0.1:8765/nope) — HTTP 404                    (код 1)
[ERROR] silent (http://127.0.0.1:8768/) — таймаут 1 с                       (код 1)
Помилка: файл конфігурації 'nope.json' не існує.                            (код 2)
Помилка конфігурації 'x.json': endpoints[1]: 'url' має починатися з http:// або https://   (код 3)
api_monitor.py: помилка: argument --timeout: значення має бути більше нуля  (код 4)
```

**Журнал** `api_monitor.log`:
```
[2026-11-17 22:31:57] [INFO] Старт перевірки: конфіг=config/monitor.json, ендпоінтів=3, таймаут=5 с
[2026-11-17 22:31:58] [SUCCESS] GitHub API (https://api.github.com) -> 200 (312 ms)
[2026-11-17 22:31:58] [INFO] Перевірку завершено: усе гаразд
```

**Перевірка без інтернету:** запустіть у окремому вікні `python -m http.server 8765`, а потім `python api_monitor.py --config config/monitor.local.json`. Ендпоінт `/` відповість 200, а `/nope` дасть 404, тобто код виходу 1.

**Прийняті рішення:**
* **Лише стандартна бібліотека (`urllib`).** Не потрібні `pip install` і віртуальне середовище. Альтернатива `requests` зручніша, але додає залежність.
* **JSON, а не YAML.** JSON читається стандартною бібліотекою. YAML потребував би PyYAML.
* **Окремий обробник таймаутів.** Таймаут читання відповіді не обгортається в `URLError`, тож без власного `except` програма падала б із трасуванням.
* **Конфігурація перевіряється до першого запиту.** Помилка в конфігу (код 2 або 3) відрізняється від помилки сервісу (код 1): у скриптах автоматизації це різні ситуації.
* **Власний клас парсера.** За замовчуванням `argparse` завершується з кодом 2, який у нас уже означає «немає конфігу». Тому помилки параметрів повертають код 4.
* **Журнал поруч зі скриптом,** а не в поточній теці, звідки запустили.

**Обмеження:** ендпоінти перевіряються послідовно; лише GET; немає повторних спроб і порогу «повільної» відповіді.

## 3. Git-хук `hooks/pre-commit`

Перед кожним комітом перевіряє вміст файлів, доданих в індекс, і скасовує коміт, якщо знаходить потенційний секрет: ключове слово `api_key`, `secret_key`, `password` (регістр не важливий) зі знаком `=` або `:`, чи маркер `DO_NOT_COMMIT`. Перевіряється саме та версія файлу, що потрапить у коміт, а не файл на диску. У повідомленні вказано номери рядків, але сам секрет не виводиться.

**Увімкнення** (один раз у кожному клоні, з кореня репозиторію):
```bash
git config core.hooksPath lab-03/hooks
```
Хуки не передаються разом із репозиторієм автоматично, тому цю команду виконує кожен, хто клонує репозиторій.

**Приклад спрацювання:**
```
$ echo 'PASSWORD=123' > test.txt && git add test.txt && git commit -m "test"
Помилка pre-commit: у файлі 'test.txt' (рядки: 1) виявлено потенційний секрет або маркер DO_NOT_COMMIT.
Коміт скасовано. Видаліть чутливі дані перед фіксацією змін.
(Якщо це хибне спрацювання: git commit --no-verify)
```

**Прийняті рішення:**
* **Перевірка вмісту індексу (`git show ":файл"`).** Файл на диску можна змінити після `git add`, і перевірка диска пропустила б секрет, який реально потрапить у коміт.
* **Імена файлів розділені нульовим байтом (`-z`).** Пробіли в назвах не ламають перевірку.
* **`#!/usr/bin/env bash` на початку.** Без нього Git запускає хук через `sh`, який на різних системах різний (на Linux часто `dash` без `pipefail` і `[[ ]]`).
* **Блокування замість попередження.** Секрет, що потрапив у коміт, лишається в історії навіть після видалення файлу, тому краще не допустити.

**Обмеження:** це регулярний вираз, а не повноцінний сканер. Можливі хибні спрацювання (наприклад, документація з прикладом `PASSWORD=`), і він не знайде секрет без ключового слова. Хук локальний: його можна обійти через `git commit --no-verify`, і він не працює у веб-інтерфейсі GitHub. Надійніше захищає серверне сканування (GitHub secret scanning).
